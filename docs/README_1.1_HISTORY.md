# Теплотрасса 1.1

Расчётный сервис для первого и второго этапов ЛЦТ 2026: один GeoJSON на входе, варианты подключения и проверяемая смета в GeoJSON на выходе. Вся обработка выполняется на Java 11. Веб-интерфейс — небольшой автономный стенд для загрузки, просмотра результатов и диагностики.

Версия 1.1.0 расширяет работающую версию 1.0.0: добавлены непрерывные глубины, вертикальные переходы и их стоимость. Основная модель строится вокруг заданных точек подключения. Редактор зданий, ИТП, CAD, внешние карты, Node.js и отдельная сборка фронтенда исключены из поставки.

## Полное подключение и форма трассы

Подключение каждого заданного ввода обязательно. Три варианта выбираются среди полностью подключённых сетей по стоимости работ с учётом спецпроходов и глубины и по длине новой сети/реконструкции (база 70/30) с отдельным штрафом формы маршрута. Штраф за неподключение и соответствующий переключатель убраны. Поиск использует несколько порядков построения, повторные попытки и локальную перепрокладку. Неполная сеть не выдаётся за готовое решение; при недостатке разных полных решений выводится фактическое число.

Заведомо запрещённые точки врезки отбрасываются до лимита кандидатов. Прямые и угловые коридоры проверяются до A*. Ступенчатые обходы упрощаются с сохранением стандартных углов, отступов, зданий, глубин и конечных точек. В таблице проверок и под разрезом выбранного участка показаны длина, число поворотов и препятствия для прямого соединения. Это не расчёт тепловых компенсаторов. Подробности — `docs/ALGORITHM.md`.

Сложность определяется по имеющимся дорогам, коммуникациям, спецпроходам и глубине. Характеристики грунта во входном наборе отсутствуют и не выдумываются. Показатель материала отдельно считает длину обеих труб; тариф строительства по-прежнему задан за метр пары.

В текущем обновлении труба доходит до исходной точки внутри здания через назначенный участок стены. Для каждого ввода ближайшая внешняя стена фиксируется до поиска, одинаково во всех вариантах. При равном расстоянии выбирается более длинная сторона, затем стабильный порядок координат. Остальные стены остаются препятствиями; недоступность выбранной стены даёт диагностику без переноса ввода. Фасадные дубликаты удалены; конечный участок включён в длину, профиль и стоимость. Проверки и результаты рабочего GeoJSON — в актуальном разделе `VALIDATION.md`.

## Обновление интерфейса

В интерфейсе больше нет выбора строгого/исследовательского режима, формулы ранжирования, шага поиска и бюджета секунд. Для каждого расчёта интерфейс отправляет `dataMode=scenario`, `rankingProfile=appendix` (стоимость 70%, длина 30%), `gridM=20` м — прежний максимум поля. Ограничение длительности удалено и из алгоритма, и из настроек API: все заданные кандидаты проверяются без остановки по таймеру. Больше кандидатов — шире поиск и дольше расчёт; кнопка отмены сохраняется.

Загруженные данные используются напрямую; заполненные расходы сохраняются. Для отсутствующих расходов применяется выбранная загрузка сети, по умолчанию 50%. Предупреждение об автоматической подготовке показывается только при фактическом заполнении недостающих параметров. Настройки этапа, глубины и числа кандидатов сохранены.

Блок «Состав стоимости и проверки» показывает таблицы: статьи в рублях и итог работ; результаты проверок с пределами; раскрываемую детализацию диаметров, расходов и длин. Доплата за глубину выделена как уже включённая в строительство. Технический JSON из блока убран.

Подробности обновления и проверка — `docs/UI_UPDATE.md`. PDF описывает алгоритмы исходной поставки 1.1.0; инструкции по текущему интерфейсу находятся в этом README. Контрольные расчёты при шаге 5 м в прежнем VALIDATION.md сохранены как отдельные исходные проверки и не являются результатами новых настроек 20 м.

## Оценка вариантов

В таблице показаны баллы 0…100: **больше — лучше**, 100 получает лучший из найденных вариантов. Оценка использует базу 70% стоимости и 30% длины плюс штраф поворотов: 90° — 25 условных метров, 45° — 50, 135° — 75. Прямая не штрафуется. Это предпочтение алгоритма, а не строительный норматив и не рублёвая надбавка; в стоимость входят только работы. Все точки обязательны к подключению. Это относительное сравнение найденных вариантов, а не показатель абсолютного качества проекта.

Раньше в колонке «Оценка» отображался индекс затрат из ТЗ: он увеличивался у худших вариантов и должен был минимизироваться. В текущей версии к базовому индексу добавлено влияние поворотов. Теперь этот индекс остаётся полем `score` в отчёте, а для отображения и экспорта добавлена обратная относительная оценка `rating`. Подробности — `docs/ALGORITHM.md` и `docs/UI_UPDATE.md`.

## Разрез по нажатию на трассу

После расчёта «План и глубина» нажмите на оранжевую линию новой сети. Весь участок между узлами выделится зелёным, а прямо под картой появится его продольный разрез. А и Б обозначают начало и конец. По вертикали показана глубина от поверхности земли, по горизонтали — расстояние вдоль участка; оранжевым отмечены пересекаемые коммуникации. При наведении отображаются точные расстояние и глубина.

Можно переключаться нажатием на другую линию, списком участков либо стрелками на клавиатуре, когда схема в фокусе. Кнопка «Снять выделение» и Escape закрывают разрез. Смена варианта или загрузка нового набора сбрасывает выбор. Для существующей сети, реконструкции и расчёта только в плане профиль не подставляется: интерфейс сообщает об отсутствии расчёта глубины.

## Быстрый запуск

На машине с Docker и docker-compose 1.29.2 выполните из этой папки:

```bash
docker-compose up --build -d
```

Откройте http://localhost:8080 — расчётный стенд, http://localhost:8080/swagger-ui.html — API. PostgreSQL 16 и приложение запускаются вместе; данные сохраняются в отдельных томах. Для просмотра журнала: `docker-compose logs -f server`.

Образы и Maven-зависимости нужны при первоначальной сборке. После сборки приложение работает без доступа к интернету: нет внешних карт, CDN, LLM, токенов или сетевых запросов к справочникам. Для изолированного стенда заранее перенесите образы через `docker save` / `docker load`.

Можно использовать уже собранный `release/teplotrassa-server-1.1.0.jar` с Java 11 и доступным PostgreSQL:

```bash
export DATABASE_URL=jdbc:postgresql://localhost:5432/teplotrassa
export DATABASE_USER=teplotrassa
export DATABASE_PASSWORD=teplotrassa_local
java -Xmx6g -jar release/teplotrassa-server-1.1.0.jar
```

По умолчанию требуется создать БД и пользователя с указанными именами; схема создаётся Flyway автоматически. Compose делает это за вас. При обновлении **с 1.0.0** замените исходники в том же каталоге Compose и выполните `docker-compose up --build -d`. Сохраните своё окружение, пароль БД и имена томов; схема БД не менялась. Не удаляйте тома. Если распаковали в другой каталог, Compose по умолчанию создаст другой проект и другие тома: используйте прежнее имя проекта через `docker-compose -p ИМЯ_ПРЕЖНЕГО_ПРОЕКТА up --build -d` либо обновляйте прежний каталог. Запуск версии 1.0.0 на целевой машине уже подтверждён пользователем; новый образ 1.1.0 здесь отдельно в Docker не запускался.

## Что реализовано

- Точки `oks_connection_point` с собственным расходом; также поддержан полный формат с `oks_id` и расходом `oks_future`. Трубы заканчиваются в исходных координатах. Для внутренней точки разрешён прямой вход через ближайшую стену, закреплённую до поиска; участок внутри входит в расчёт. Транзит и разветвления в здании запрещены. Дополнительные фасадные точки потребителей не создаются. Подробности — `docs/BUILDINGS.md`.
- Поиск отдельных врезок и совместных ветвей. Сравнивается полная стоимость, включая последствия для существующей сети до источника.
- Прямые отрезки и маршруты A* со штрафом за повороты, состоянием направления и точной проверкой геометрии. При подключении учитывается направление принимающего участка. Внутренние повороты — 45°/90°; присоединения к оси — 45°/90° либо продолжение направления.
- Расходы на общих ветвях суммируются один раз для пары труб; DN выбирается из таблицы приложения. Длина проверяется для связной компоненты одного DN с суммой длин всех ветвей. При необходимости допускается увеличение только на одну номенклатуру относительно DN по расходу.
- Камеры в разветвлениях, предел четыре примыкающих участка, правило 10 м и стоимость независимых врезок. Рассматриваются подходящие камеры, а не только ближайшая.
- Реконструкция только затронутой части существующей трубы. Несколько врезок суммируются на общей части; коэффициенты спецпрохода к реконструкции не применяются. Используемая для врезки существующая камера реконструируется и оплачивается один раз.
- Пространственные отступы с учётом габарита пары труб; спецучастки, технические узлы при смене параметров и максимальный коэффициент при перекрытии спецпроходов.
- Глубина до верха новой пары труб, постоянные площадки пересечений, уклоны до 0,10, согласование общих камер, подъёмы/заглубления и коэффициент удорожания.
- До трёх различных полных вариантов из многостартового поиска, без экономического отказа от домов. Обход новых ветвей, повторные подключения, локальная перепрокладка и упрощение изгибов. Если полное решение не найдено, выводятся диагностика и пустой список готовых вариантов.
- Потоковая загрузка, дисковое хранение, PostgreSQL со spatial GiST-индексом, ограниченная очередь расчётов, отмена, изоляция рабочих сессий, Swagger и потоковая выгрузка.

## Как проверить глубины

1. Нажмите **Пример с газом и кабелем**. Кнопка включает режим «План и глубина» и задаёт 3 кандидата врезки для воспроизведения контрольного прогона.
2. Оставьте правила приложения, минимальную глубину 0,7 м и максимальную 6 м. Нажмите «Рассчитать все точки».
3. Нажмите на новый участок на схеме. Он станет зелёным, под картой откроется «Продольный разрез». Разверните пересечения для проверки зазоров. Разрез показывает рассчитанные подъёмы и заглубления. Числа старого контрольного расчёта относятся к шагу поиска 5 м; в текущем интерфейсе шаг зафиксирован на 20 м.
4. Скачайте GeoJSON и отчёт. В GeoJSON глубины записаны в `depth_start`/`depth_end`, третья координата `Z=-h`. Отчёт содержит станции профиля, зазоры и доплату.

API по умолчанию сохраняет `mode=plan` ради совместимости; тестовый интерфейс по умолчанию выбирает `depth`. Настройки: `depthRuleProfile=appendix|protocol`, `minDepthM=0.7`, `maxDepthM=6`. Диапазон глубин задаётся без дискретизации 0,5 м. Полная модель, формулы и ограничения — `docs/DEPTH.md`.

## Как запустить приложенный набор

1. Загрузите `examples/supplied.geojson` — это копия исходного файла без изменений.
2. Откройте диагностику. В нём отсутствуют `flow_tph` и `upstream_object_id` существующих труб, а у камер также отсутствует `diameter`. Правило `railway` в приложении не задано.
3. Задайте загрузку сети, например 50%, и запустите расчёт. Исследовательский режим применяется автоматически. Топология восстанавливается по соединённым концам с допуском 0,25 м; разрывы не дорисовываются. Железная дорога считается запрещённой зоной с отступом 1 м плюс половина ширины новой сети.
4. Для окончательной сметы заполните действительные исходные расходы, направления к источнику и правила ограничений, после чего при необходимости используйте строгую проверку через API. Интерфейс также сохранит заполненные исходные расходы.

Загрузка 50% — половина табличной пропускной способности каждого существующего DN, **не оценка фактической загрузки**. Неполный набор никогда не обозначается как полный. Принятые настройки записываются в отчёт и метаданные результата.

`examples/complete.geojson` — отдельный небольшой пример с полными исходными атрибутами. Его можно загрузить кнопкой «Загрузить проверочный пример» и сразу рассчитать с предустановленными параметрами.

## Проверки и результаты

Готовые расчёты и результаты проверок находятся в `validation/`. В `VALIDATION.md` указаны конфигурация, числовые итоги и границы выполненной проверки.

```bash
mvn -f server/pom.xml test
mvn -f server/pom.xml -DsuppliedDepthDataset=true test
mvn -f server/pom.xml -DsuppliedDataset=true -Dtest=SuppliedDatasetTest test
mvn -f server/pom.xml -DlargeFiles=true -Dtest=StreamingSizeTest test
mvn -f server/pom.xml -DloadUsers=true -Dtest=Load50Test test
```

Команда с `largeFiles` проверяет потоковое чтение файла 3 ГиБ с одним объектом и пробельным заполнением. Она не заменяет испытание городского набора с миллионами геометрий. H2 применяется только в тестах; штатная база — PostgreSQL.

## Эксперимент с нейросетью, 20.09.2026

Добавлена небольшая обученная модель MLP, которая в экспериментальном режиме ранжирует места подключения перед трассировкой. Веса поставляются в JAR; Python и GPU для работы сервиса не нужны. Ближайшие стены, исходные точки, предпочтение 90° перед 45°, все обязательные подключения, DN и глубины проверяет прежний алгоритм.

Обучение выполнено на синтетических кварталах. На 16 отложенных кварталах итоговые оценки совпали для поиска без ускорения, математического отсечения и гибрида. Нейросеть улучшила порядок первого перспективного кандидата, но дополнительного сокращения поисков и улучшения финальных трасс не показала. На исходном квартале гибрид сохранил все вводы, но потерял лучший прежний вариант. Поэтому по умолчанию сохранён прежний расчёт; модель доступна как отдельный эксперимент, без обещания выигрыша. Подробности и ограничения — `docs/NEURAL_ROUTING.md`.

Параметр API `neuralGuidance`: `baseline` (по умолчанию, прежний расчёт), `on` (эксперимент с моделью), `bounds` (эксперимент с отсечением без модели), `off` (то же исправленное геометрическое ядро, без отсечения и модели). Для изолированного сравнения модели используйте `off`, `bounds`, `on`. Интерфейс продолжает запускать прежний режим. Статистика и идентификатор модели находятся в `search.neuralGuidance` отчёта.
